## ১. নির্দেশনার সারাংশ ও তার তাৎপর্য

### ১.১ আপনি যা জানিয়েছেন (নিশ্চিত তথ্য)

| # | তথ্য | স্থাপত্যগত ফলাফল |
|---|---|---|
| 1 | **Amar Somobay একটি multi-tenant সমবায় প্ল্যাটফর্ম** | একটি ডেটাবেস/কোডবেস, অনেক সমিতি (tenant)। প্রতিটি টেবিলে `org_id` বাধ্যতামূলক — এটি আগে থেকেই আছে (§01 স্পেক)। এখন এটি **অস্থায়ী ডিফল্ট নয়, নিশ্চিত নির্দেশ**। |
| 2 | **Platform Admin / Super Admin = প্ল্যাটফর্মের মালিক** | নতুন স্তর: Platform layer। বিদ্যমান স্পেকে `PLATFORM_ADMIN` রোলটি ছিল (রোল #10) কিন্তু তার কোনো পেজ ডিজাইন হয়নি। এখন তার **স্পষ্ট ভূমিকা**: টেনান্ট অনুমোদন, প্ল্যান বরাদ্দ, প্ল্যাটফর্ম স্বাস্থ্য। |
| 3 | **Org Admin / সমিতির মালিক-ব্যবস্থাপক প্ল্যাটফর্মে সমিতি পরিচালনার জন্য আবেদন করেন** | নতুন প্রবাহ: **Org Onboarding** (আবেদন → যাচাই → প্রোভিশনিং)। এটি সমিতির নিজস্ব Admin Panel-এর **আগের** ধাপ। |
| 4 | **Super Admin SaaS প্ল্যান অনুযায়ী সমিতি পরিচালনার অনুমতি দেন** | নতুন স্তর: **Subscription + Entitlement**। কোন সমিতি কোন মডিউল ব্যবহার করতে পারবে, কত সদস্য, কত স্টাফ, কত SMS — সব প্ল্যান থেকে নির্ধারিত। |
| 5 | **Super Admin কন্ট্রোল প্যানেল এখন ডিজাইন করা হচ্ছে না** | P-কোডের পেজগুলো এই রিপোর্টে **শুধু তালিকা ও ডেটা-হুক পর্যন্ত**। ডিজাইন পরে। কিন্তু **এখনই** ডেটা মডেলে জায়গা রাখতে হবে, নইলে পরে সব টেবিল বদলাতে হবে। |
| 6 | **৩টি Savings Scheme Category**: General Cooperative Savings · ROSCA · Joint Goal | তিনটি **আলাদা ক্যাটাগরি**, একই "স্কিম" নয়। বিদ্যমান ৬৭ পেজ/১০২ স্ক্রিন = শুধু **General Savings (GS)** ক্যাটাগরি। |
| 7 | **General Savings = প্রাথমিক Design Reference** | বিদ্যমান সব ডিজাইন টোকেন, ৬টি মোবাইল প্যাটার্ন, ৫-স্লট নেভ চুক্তি, রোলভিত্তিক শেল (D-35), ৭টি বাধ্যতামূলক অবস্থা, BR-01…BR-15, R-01…R-08 — **সব নতুন মডিউলেও একইভাবে প্রযোজ্য**। নতুন করে ডিজাইন ভাষা বানানো হবে না। |
| 8 | **Qard Hasanah = সম্পূর্ণ স্বতন্ত্র মডিউল**, সুদমুক্ত ঋণ সহায়তা | Savings-এর চতুর্থ ক্যাটাগরি **নয়**। আলাদা ওয়ার্কফ্লো, আলাদা হিসাবের খাত, আলাদা ড্যাশবোর্ড, আলাদা নম্বরিং। |
| 9 | **QH-তে শুধু বিদ্যমান সদস্যরা আবেদন করতে পারবে, এবং সবাই স্বয়ংক্রিয়ভাবে পারবে না** | নতুন ইঞ্জিন: **Eligibility Engine**। এটিই পুরো প্ল্যাটফর্মের সবচেয়ে জটিল নতুন অংশ (§৭)। |
| 10 | **Admin-এর হাতে সম্পূর্ণ Eligibility Configuration ও Application Control** | নিয়ম-ভিত্তিক কনফিগারেশন (কোড লেখা নয়), সীমা, কোটা, জানালা, ম্যানুয়াল এক্সেপশন, অডিট। |
| 11 | **কোনো সুদ, সুদের হিসাব বা সুদভিত্তিক চার্জ নেই** | বিদ্যমান **BR-13** এখন **চারটি মডিউলেই** প্রযোজ্য। QH-তে `interest_*` ফিল্ড থাকবে না; repayment = **শুধু মূলধন (principal only)**। |
| 12 | **সব মডিউল একই Member Management ও Authentication-এর সাথে সমন্বিত** | একটি `members` টেবিল, একটি লগইন, একটি KYC — চার মডিউলে একই সদস্য-পরিচয়। সদস্যকে চারবার নিবন্ধন করা যাবে না। |
| 13 | **সব আর্থিক কার্যক্রমের হিসাব, অনুমোদন ও Audit Trail নিশ্চিত করতে হবে** | একটি **একক লেজার** (`ledger_entries`), একটি অনুমোদন ইঞ্জিন (BR-04 maker≠checker), একটি অপরিবর্তনীয় অডিট লগ (D-30) — চার মডিউলের সব লেনদেন সেখানেই পোস্ট হবে। |

```
│    অনুমোদন ইঞ্জিন (BR-04) · অডিট লগ · নোটিফিকেশন · ডকুমেন্ট ·     │
│    দিন/মাস সমাপ্তি · রিকনসিলিয়েশন · রিপোর্ট ইঞ্জিন · অফলাইন sync │
├──────────────────────────────────────────────────────────────────┤
│ ৫. PRESENTATION LAYER                                            │
│    Member = মোবাইল অ্যাপ · Admin = মোবাইল অ্যাপ + Desktop        │
│    Dashboard · একই Backend/API/নিয়ম, শুধু UI আলাদা (D-35 ✅)     │
└──────────────────────────────────────────────────────────────────┘
```

**মূল কথা:** স্তর ৪ (Shared Kernel) **একবারই** তৈরি হবে এবং চারটি মডিউলই সেটি ব্যবহার করবে। মডিউল বাড়লেও হিসাবের ইঞ্জিন, অনুমোদন ইঞ্জিন বা অডিট লগ দ্বিতীয়বার বানানো হবে না। এটিই আপনার "একই Member Management ও Authentication-এর সঙ্গে সমন্বিত" নির্দেশের স্থাপত্যগত রূপ।

### ২.২ টেনান্সি আইসোলেশন — তিনটি বিকল্প

| বিকল্প | কীভাবে | সুবিধা | ঝুঁকি | মন্তব্য |
|---|---|---|---|---|
| **(ক) এক ডেটাবেস + `org_id` (Row-Level Security)** — 🟡 **সুপারিশ** | সব টেবিলে `org_id`; DB-স্তরে RLS পলিসি; প্রতিটি API কলে টেনান্ট কনটেক্সট বাধ্যতামূলক | সরল, খরচ কম, ক্রস-টেনান্ট রিপোর্ট সহজ, বিদ্যমান ডেটা মডেল অপরিবর্তিত | একটি বাগে অন্য সমিতির ডেটা দেখা যেতে পারে → RLS + অটোমেটেড টেনান্ট-টেস্ট বাধ্যতামূলক | বিদ্যমান স্পেক (§01) এই পথেই আছে — **কোনো নতুন কাজ নয়, শুধু কঠোর প্রয়োগ** |
| (খ) Schema-per-tenant | প্রতি সমিতির আলাদা স্কিমা | আইসোলেশন বেশি | মাইগ্রেশন × N, খরচ বেশি, প্ল্যাটফর্ম রিপোর্ট কঠিন | বড় এন্টারপ্রাইজ টেনান্ট এলে পরে বিবেচ্য |
| (গ) Database-per-tenant | প্রতি সমিতির আলাদা DB | সর্বোচ্চ আইসোলেশন | পরিচালনা ব্যয় সবচেয়ে বেশি | শুধু যদি কোনো সমিতি আইনগতভাবে আলাদা DB দাবি করে |

⚠️ **[DECISION D-36]** কোন আইসোলেশন মডেল? (সুপারিশ: **ক**, সাথে RLS + টেনান্ট-লিক টেস্ট)

> **অলঙ্ঘ্য নিয়ম (যেকোনো বিকল্পেই):** প্রতিটি আর্থিক রেকর্ডে `org_id`; কোনো কুয়েরি `org_id` ছাড়া চলবে না; অফলাইন sync-এও টেনান্ট আইডি বাধ্যতামূলক; **সদস্য এক সমিতি থেকে অন্য সমিতিতে স্বয়ংক্রিয়ভাবে দেখা যাবে না** (একই NID দিয়ে দুই সমিতিতে আলাদা সদস্যপদ সম্ভব — D-16 শুধু এক সমিতির ভেতরে প্রযোজ্য) ⚠️ **[DECISION D-36-খ]**।

### ২.৩ সমিতির জীবনচক্র (Org Lifecycle) — নতুন State Machine

```

                     │                        ▲                 │
                     ▼                        └─────────────────┘
              [অনুমোদিত] ──► [প্রোভিশনড] ──► [সক্রিয় (সাবস্ক্রাইবড)]
                     │                              │
                     ▼                              ▼
              [প্রত্যাখ্যাত]              [গ্রেস (পেমেন্ট ব্যর্থ)]
                     │                              │
                     └──► [আর্কাইভ] ◄── [স্থগিত] ◄───┘
                                          │
                                          ▼
                                   [অফবোর্ডড + ডেটা রপ্তানি]
```

| অবস্থা | কে বদলায় | কী হয় | অডিট |
|---|---|---|---|
| খসড়া আবেদন | Org Admin (আবেদনকারী) | সমিতির নাম, নিবন্ধন নম্বর, নিবন্ধকের দপ্তর, উপ-আইন, কমিটি তালিকা, প্রত্যাশিত সদস্য সংখ্যা, প্রয়োজনীয় মডিউল | হ্যাঁ |
| যাচাইয়ের অপেক্ষায় | Platform Admin | নথি যাচাই, নিবন্ধন নম্বরের সত্যতা, প্রয়োজনে অতিরিক্ত তথ্য চাওয়া | হ্যাঁ |
| অনুমোদিত + প্রোভিশনড | Platform Admin | টেনান্ট তৈরি, প্রথম ORG_ADMIN অ্যাকাউন্ট, ডিফল্ট সেটিংস, **প্ল্যান ও এনটাইটেলমেন্ট বরাদ্দ** | হ্যাঁ |
| সক্রিয় | স্বয়ংক্রিয় | সমিতির Admin Panel পুরোপুরি খোলে; প্ল্যানের বাইরের মডিউল **লকড অবস্থায় দৃশ্যমান** থাকবে (কেন লকড তা ব্যাখ্যাসহ) | — |
| গ্রেস / স্থগিত | Platform Admin | লেনদেন বন্ধ, **পঠন ও ডেটা রপ্তানি খোলা** থাকবে (সদস্যের টাকা আটকে রাখা যাবে না) | হ্যাঁ + সমিতি ও সদস্যকে নোটিশ |
| অফবোর্ডড | Platform Admin + Org Admin | সম্পূর্ণ ডেটা রপ্তানি (CSV/PDF/JSON), সংরক্ষণ মেয়াদ পর্যন্ত আর্কাইভ (D-30), লেজার অপরিবর্তিত | হ্যাঁ |

⚠️ **[DECISION D-43]** প্ল্যান ও এনটাইটেলমেন্টের মাত্রা কী হবে? · ⚠️ **[DECISION D-65]** অফবোর্ডিং-এ ডেটা রপ্তানির ছক ও সংরক্ষণ দায়িত্ব কার?

> **গুরুত্বপূর্ণ নীতি:** প্ল্যান শেষ হলে বা সমিতি স্থগিত হলেও **সদস্যের টাকা ও হিসাবের ইতিহাস মুছে ফেলা যাবে না** — লেজার অ্যাপেন্ড-অনলি (R-02) এবং আর্কাইভ নীতি (D-30) প্ল্যাটফর্ম স্তরেও একইভাবে প্রযোজ্য।

### ২.৪ প্ল্যান → এনটাইটেলমেন্ট মডেল (প্রস্তাব)

একটি প্ল্যান কিছু **এনটাইটেলমেন্ট** দেয়; সমিতির সাবস্ক্রিপশন সেই এনটাইটেলমেন্টের একটি **স্ন্যাপশট** রাখে (পরে প্ল্যান বদলালে পুরনো সমিতির শর্ত নীরবে বদলে যাবে না — D-32-এর একই যুক্তি)।

| এনটাইটেলমেন্ট মাত্রা | উদাহরণ | UI-তে প্রভাব |
|---|---|---|
| **মডিউল অন্তর্ভুক্তি** | General Savings ✅ · ROSCA ✅ · Joint Goal ❌ · Qard Hasanah ✅ | বন্ধ মডিউলের মেনুতে তালা + "আপনার প্ল্যানে নেই — Super Admin-এর সাথে যোগাযোগ" ব্যাখ্যা |
| **সদস্য সীমা** | সর্বোচ্চ ৫০০ সদস্য | নিবন্ধনে সীমা ছাড়ালে আটকাবে + আগাম সতর্কতা (৯০%) |
| **স্টাফ সিট** | সর্বোচ্চ ৮ ব্যবহারকারী | A-37/AM-34-এ স্টাফ যোগ করার সীমা |
| **সার্কেল/গোল সীমা** | একসাথে ৩টি ROSCA সার্কেল, ৫টি Joint Goal | তৈরির সময় যাচাই |
| **QH ফান্ড পুল/কোটা** | মাসে সর্বোচ্চ ৳৫,০০,০০০ বিতরণ | Eligibility Engine-এ Window/Quota স্তর (§৭.২ স্তর ৪) |

| **সংরক্ষণ মেয়াদ** | ৮ বছর (D-30 এর চেয়ে কম হতে পারবে না) | আর্কাইভ নীতি — **আইনগত নিম্নসীমার নিচে প্ল্যান বিক্রি করা যাবে না** |
| **সাপোর্ট স্তর** | ইমেইল / ফোন / নিবেদিত ম্যানেজার | শুধু সহায়তা পেজে প্রভাব |

### ২.৫ Platform Admin-এর ক্ষমতার সীমা (অলঙ্ঘ্য)

| করতে পারবে | করতে পারবে **না** |
|---|---|
| সমিতির আবেদন অনুমোদন/প্রত্যাখ্যান | কোনো সমিতির লেনদেন এন্ট্রি/সংশোধন |
| প্ল্যান, সাবস্ক্রিপশন, এনটাইটেলমেন্ট বরাদ্দ | সদস্যের ব্যালেন্স বা স্কিমের নিয়ম বদল |
| মডিউল ফিচার ফ্ল্যাগ চালু/বন্ধ | অনুমোদন কিউতে অংশগ্রহণ (maker/checker নয়) |
| প্ল্যাটফর্ম অডিট লগ দেখা | সমিতির অডিট লগ **বদলানো** (পঠন সীমিত, কারণসহ লগ করা) |
| টেনান্ট স্থগিত/অফবোর্ড + ডেটা রপ্তানি | সমিতির নগদ/ব্যাংক হিসাবে হাত দেওয়া |
| **Break-glass** (জরুরি প্রবেশ) — শুধু লেখা অনুমতি + দ্বিতীয় Platform Admin-এর অনুমোদন + সমিতির ORG_ADMIN ও AUDITOR-কে স্বয়ংক্রিয় অ্যালার্ট | গোপন প্রবেশ — কোনো প্রবেশই অলগড নয় |

> এটি বিদ্যমান স্পেকের D-13 নোটের ("কোনো সমিতির আর্থিক ডেটা এডিট নয়") সরাসরি প্রসারণ এবং **BR-04 (maker ≠ checker)** প্ল্যাটফর্ম স্তরেও প্রযোজ্য।

### ২.৬ এখন ডিজাইন না করলেও **এখনই** যা ঠিক করতে হবে

Super Admin প্যানেল পরে বানানো হবে — ঠিক আছে। কিন্তু নিচের ৭টি জিনিস এখনই ডেটা মডেল ও স্পেকে ঢোকাতে হবে, নইলে পরে বিদ্যমান ১০২ স্ক্রিনের ডেটা কাঠামো বদলাতে হবে:

1. `organizations`-এ টেনান্ট অবস্থা ও আবেদন রেফারেন্স (`lifecycle_status`, `application_id`, `approved_at`, `approved_by`)
2. `plans`, `subscriptions`, `entitlements` (স্ন্যাপশটসহ)
3. `modules` (রেজিস্ট্রি) ও `org_modules` (কোন সমিতির কোন মডিউল চালু, কোন ভার্শন থেকে)
4. `schemes`-এ **`category`** ফিল্ড (`general` / `rosca` / `joint_goal`) — বিদ্যমান সব স্কিমের জন্য ডিফল্ট `general`
5. প্রতিটি আর্থিক এনটিটিতে **`module_key`** — যাতে একটি লেজারে চার মডিউলের লেনদেন আলাদা করে চেনা যায়
6. প্ল্যাটফর্ম-স্তরের আলাদা `platform_audit_logs` (সমিতির অডিট লগের সাথে মেশানো যাবে না)
7. নম্বরিং প্যাটার্নের সাথে মডিউল উপসর্গ (§৪.৬)

**সিদ্ধান্ত:** এই চারটির **গাণিতিক মডেল, ঝুঁকি ও হিসাবের খাত আলাদা**। একই `savings_accounts` টেবিলে ঢুকিয়ে দিলে (১) ব্যালেন্সের অর্থ অস্পষ্ট হয়ে যাবে, (২) রিপোর্ট ভুল হবে, (৩) নিরীক্ষা অসম্ভব হবে। তাই:

- **GS / RS / JG** = তিনটি পৃথক `scheme_category`, প্রতিটির নিজস্ব contract entity, কিন্তু একই "সঞ্চয়" পরিবার (টাকা সদস্যের দিকে থাকে)।
- **QH** = পৃথক `module_key`, নিজস্ব লাইফসাইকেল ও খাত (টাকা সমিতির দিকে ফেরত আসে)। সঞ্চয় পরিবারের **অংশ নয়**।

### ৫.৫ QH-তে সদস্যের অভিজ্ঞতা — যোগ্যতা স্বচ্ছতা

সবচেয়ে সংবেদনশীল মুহূর্ত: **কেউ আবেদন করতে পারছে না।** তিনটি নীতি:

1. **কারণ বলতেই হবে, কিন্তু সম্মান রক্ষা করে।** "আপনি অযোগ্য" নয় — "আপনার সঞ্চয় অ্যাকাউন্টে ৳১,০২০ বকেয়া আছে; পরিশোধ করলে আবেদন করতে পারবেন" (কারণ-কোড থেকে তৈরি বাক্য, §৭.৪)।
2. **আগেই দেখাতে হবে, আবেদনের মাঝপথে নয়।** QH কার্ডেই অবস্থা; আবেদন বাটন নিষ্ক্রিয় হলে পাশে "কেন" লিংক। (বিদ্যমান BR-05-এর একই যুক্তি — হতাশা কমানো।)
3. **সীমা আগেই জানানো।** "আপনি সর্বোচ্চ ৳২০,০০০ পর্যন্ত আবেদন করতে পারবেন" — যাতে আবেদন করে প্রত্যাখ্যাত হতে না হয়।

**যোগ্যতার তিনটি দৃশ্যমান অবস্থা:**

| শর্তসাপেক্ষ | অ্যাম্বার ব্যাজ + শর্তের তালিকা | "আর ২টি শর্ত পূরণ হলে আবেদন করতে পারবেন" |

### ৫.৬ ROSCA ও Joint Goal-এ সদস্যের অভিজ্ঞতা

**ROSCA:** সিট কার্ডে চারটি তথ্য সবসময় — (১) আমি কত জমা দিয়েছি, (২) আমি পেয়েছি কি না (কবে, কত), (৩) পরবর্তী ড্র কবে, (৪) বাকি কারা পায়নি। ড্রয়ের ফলাফল প্রকাশের সাথে সাথে নোটিফিকেশন; ড্র ইতিহাস অপরিবর্তনীয়ভাবে দেখানো (সন্দেহ এড়াতে)।
**Joint Goal:** প্রগ্রেস রিং + লক্ষ্য তারিখের কাউন্টডাউন + আমার অবদান বনাম প্রতিশ্রুতি + লক্ষ্য অর্জিত হলে টাকা কীভাবে ব্যবহৃত হলো তার **প্রমাণসহ বিবরণ** (স্বচ্ছতা = আস্থা)।

## ৬. Admin Panel — মডিউলভিত্তিক Control ও Configuration

### ৬.১ নেভিগেশনের প্রভাব — সমস্যা ও সমাধান

বিদ্যমান ANAV = **৬ গ্রুপ · ২৫ আইটেম**; ড্রয়ারে সব, বটম নেভে রোলের শীর্ষ ৫টি (D-35)। তিনটি নতুন মডিউল যোগ করলে আইটেম সংখ্যা **২৫ → ~৬০** হবে। একটি ড্রয়ারে ৬০ আইটেম = ব্যবহারযোগ্য নয়।

| বিকল্প | বর্ণনা | রায় |
|---|---|---|
| (ক) এক বিশাল ANAV | সব মডিউলের সব আইটেম এক ড্রয়ারে | ❌ খুঁজে পাওয়া যাবে না |
| (খ) **মডিউল সুইচার + মডিউল-স্কোপড ANAV** — 🟡 **সুপারিশ** | ড্রয়ারের উপরে মডিউল বাছাই (সঞ্চয় · চক্র · লক্ষ্য · কর্জে হাসানা · ব্যবস্থাপনা); নিচে শুধু সেই মডিউলের গ্রুপ (~৮–১২ আইটেম)। বটম নেভ **রোলভিত্তিকই থাকে**, তবে সক্রিয় মডিউলের প্রধান কাজে যায় | ✅ |
| (গ) আলাদা আলাদা অ্যাপ/ট্যাব per মডিউল | প্রতিটি মডিউল আলাদা এলাকা | ❌ এক স্টাফ একই দিনে চার মডিউলে কাজ করে; বারবার সুইচ ক্লান্তিকর |

**সুপারিশ (খ)-এর চুক্তি:**
- বটম নেভের **৫-স্লট চুক্তি অপরিবর্তিত** (repeat(5,1fr)) — কখনো ৬টি নয়।
- রোলভিত্তিক শেল (Shell-A…E) অটুট; শুধু প্রতিটি শেলের নেভ টার্গেট **মডিউল-সচেতন** হবে (যেমন ACCOUNTANT-এর "কিউ" ট্যাব সক্রিয় মডিউলের অনুমোদন কিউতে যায়)।
- `AMNAV_SCREEN` ম্যাপের প্রসারণ: প্রতিটি AM স্ক্রিনের সাথে ANAV কী + মডিউল কী।
- প্ল্যানে মডিউল বন্ধ থাকলে ড্রয়ারে সেটি **তালাসহ দৃশ্যমান** (লুকানো নয়) — কারণ ও করণীয় ব্যাখ্যাসহ (§২.৪)।

4. নিয়ম **পরিবর্তনযোগ্য**, কিন্তু পরিবর্তন **ভার্শনকৃত**; পুরোনো আবেদন পুরোনো নিয়মে বিচারিত (BR-14-এর অনুকরণ)।

### ৭.৬ কোটা, জানালা ও প্রতিযোগিতা

- **জানালা:** Admin তারিখসহ জানালা খুলবে/বন্ধ করবে (যেমন ১–১৫ নভেম্বর)। বন্ধ জানালায় আবেদন বাটনই নিষ্ক্রিয় + পরবর্তী জানালার তারিখ।
- **কোটা:** তিন স্তরে — সমিতিভিত্তিক মাসিক মোট, শাখা/রুটভিত্তিক, এক সদস্যের সর্বোচ্চ সক্রিয় আবেদন।
- **কোটা পূর্ণ হলে কী হবে:** ⚠️D-51 — (ক) সরাসরি বন্ধ, (খ) ওয়েটলিস্টে রাখা (পরের জানালায় অগ্রাধিকার), (গ) শুধু সতর্কতা। 🟡 প্রস্তাবিত ডিফল্ট: (ক) + Admin চাইলে (খ) চালু করতে পারবে।
- **রেস কন্ডিশন:** একই মুহূর্তে দুটি আবেদন শেষ কোটা নিতে চাইলে → ডেটাবেস-স্তরে লক + `idempotency_key`; পরাজিত আবেদনকারীকে স্পষ্ট বার্তা (কোড QH-B-08)।

## ৮. নতুন পেজ ইনভেন্টরি ও User Flow পরিকল্পনা

> ⚠️ **এই সংখ্যাগুলো প্রাথমিক (provisional)।** §১৩-এর সিদ্ধান্ত (বিশেষত D-42, D-46, D-51, D-52, D-55, D-56) চূড়ান্ত না হওয়া পর্যন্ত পেজ সংখ্যা ±১০% বদলাতে পারে। ডিজাইন শুরু হবে সিদ্ধান্তের পরে।

### ৮.১ গণনার নিয়ম (বিদ্যমান স্পেক §৫.০ অপরিবর্তিত)

1. মোডাল, ড্রপডাউন, কনফার্মেশন ডায়ালগ, টোস্ট = **পেজ নয়**।
2. একই পেজ Member ও Admin দুজনে ব্যবহার করলে = **২টি পেজ** (উপস্থাপনা আলাদা)।
3. Shared Component = পেজ নয়।
4. Admin Web (Desktop) + Admin App (Mobile) একই পেজের **দুটি প্রেজেন্টেশন** = লজিক্যাল পেজ ১, কিন্তু স্ক্রিন ২।
5. Settings-এর সাব-প্যানেল (D-34) = আলাদা পেজ নয়, ট্যাব/সাব-সেকশন।
6. প্ল্যাটফর্ম পেজ (P-) এই মুহূর্তে **ডিজাইন হবে না**, তাই মোট সংখ্যায় আলাদা করে দেখানো হয়েছে।

1. **একটি অ্যাট্রিবিউটেই সব** — যেকোনো কনটেইনারে `data-theme="qh"` (বা `data-module="qard_hasanah"`) দিলেই তার ভেতরের সব স্ক্রিন সেই থিমে রঙ হবে।
2. **ডিফল্ট অক্ষুণ্ণ** — `data-theme` না থাকলে `ui.css`-এর বিদ্যমান ডিজাইন হুবহু থাকে। `skins.css`-এর প্রতিটি রুল `[data-theme…]`/`[data-module…]`/`.qh-`/`.sk-`-এ স্কোপড; তাই বিদ্যমান কোনো রুল ওভাররাইড হয় না (যাচাই: `/tmp/tsk2.mjs`, ১৮৩টি রুল অডিট)।
3. **টোকেন ব্রিজ** — প্রতিটি স্কিন ২৫টি `--mod-*` টোকেন সংজ্ঞায়িত করে (QH-তে সোনালি টোকেনসহ ৩০টি); একটি ব্রিজ রুল সেগুলোকে বিদ্যমান `--green-*`, `--lime`, `--lime-soft`, `--green`, `--mint` টোকেনে ম্যাপ করে। ফলে ১০২টি স্ক্রিনের একটি মার্কআপও বদলাতে হয় না।
4. **স্ট্যাটাস রঙ স্থির** — সফল/বিপদ/সতর্ক/তথ্য রঙ কোনো স্কিনে বদলায় না; ৭টি বাধ্যতামূলক অবস্থা (Normal · Empty · Loading · Error · Permission · Offline · Blocked) সব থিমে একই অর্থ দেয়।
5. **সুদমুক্ত ভাষা বাধ্যতামূলক** — কোনো স্কিনে সুদ/ইন্টারেস্ট/মুনাফা/ঋণের দাম হিসাব বা লেবেল যোগ করা যাবে না (BR-13 → BR-20)। QH স্ক্রিনে প্রতিটি অঙ্কের পাশে **"সুদ ৳০"**।
6. **অ্যাক্সেসিবিলিটি** — প্রতিটি টেক্সট জোড়ায় WCAG AA (≥ ৪.৫:১), প্যাটার্ন ≤ ২২% অস্বচ্ছতায়, `prefers-reduced-motion`/`prefers-contrast`/`@media print` সম্মানিত।

**প্রয়োগ (React প্রোটোটাইপে):** রাউটে মডিউল চিহ্নিত → রুট কনটেইনারে `data-theme`/`data-module` → `skins.css` একবার গ্লোবালি লোড → QH মডিউলে কিট কম্পোনেন্ট যোগ → প্রতিটি অঙ্কে "সুদ ৳০" নিশ্চিত করা। বিদ্যমান কম্পোনেন্ট লাইব্রেরি বদলাতে হয় না।
