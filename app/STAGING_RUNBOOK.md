**উদ্দেশ্য:** staging-এ D-01 (সুদমুক্ত) ও D-02 (cross-tenant isolation) যাচাই করা — এমনভাবে যাতে
কোনো আর্থিক ডেটা না বদলায়, আর প্রতিটি ধাপের ফলাফল রিপোর্টে লেখা যায়।

**কঠোর নিয়ম**
1. এই রানবুকের **কোনো ধাপ production-এ চালানো যাবে না**।
2. `*_DRAFT.sql` / `*_REMEDIATION_DRAFT.sql` — **অনুমোদন ছাড়া চালানো নিষিদ্ধ**।
3. `MULTI_TENANT_FOUNDATION_DOWN.sql` — **কখনোই নয়** (এটি `USING(true)` নীতি ফিরিয়ে আনে)।
4. কোনো `DROP COLUMN` / `DROP TABLE` নেই; আর্থিক সারি UPDATE নেই।
5. প্রতিটি ধাপের পর: **Test Results · Security Findings · Residual risk** রিপোর্ট।

## ৩ · ধাপ ১ — Read-only অডিট (নিরাপদ)

দুটি ফাইল, দুটোই **শুধু SELECT** — কোনো সারি বদলায় না।

| ফাইল | কুয়েরি | কী বের করে |
|---|---|---|
| `app/db/D01_zero_interest__AUDIT_ONLY.sql` | ১১ | সুদ/মুনাফা-সদৃশ কলাম · `somobay_plans.profit_percentage`-এর অবস্থা · **শূন্য-লঙ্ঘন** (কোন স্কিমে হার ≠ ০) · কোন সমবায়ে · প্রভাবের পরিধি · পেমেন্ট টাইপ · ফাংশন/ট্রিগার/ভিউ নির্ভরতা · বিদ্যমান CHECK · বিলম্ব-ফি-র বর্তমান অবস্থা (তথ্যের জন্য) · সারসংক্ষেপ |
| `app/db/D02_tenant_isolation__AUDIT_ONLY.sql` | ১১ | সব RLS নীতি + `USING(true)` ঝুঁকি · RLS-বিহীন টেবিল · `SECURITY DEFINER` + `search_path` · `organization_id` NULL/হার্ডকোডেড · গ্লোবাল `profiles.role='admin'` অথচ সদস্যপদ নেই · বৈশ্বিক-রোল নির্ভর নীতি · anon/authenticated-এ সরাসরি GRANT · Storage বাকেট/নীতি · Realtime publication · tenant-integrity ট্রিগার · সারসংক্ষেপ |

চালানোর নিয়ম:
1. staging-এর SQL editor-এ **একটি ফাইল একবারে** চালান; ফলাফল প্রতিটি কুয়েরি-নম্বর ধরে কপি করুন।
2. ফলাফল `reports/`-এ নতুন ফাইলে যুক্ত করুন (নাম-প্রস্তাব: `d01-d02-audit-YYYY-MM-DD.md`)।
3. স্ক্রিনশট/CSV সংযুক্ত করলে আরও ভালো — কিন্তু **আসল সদস্যের নাম/মোবাইল/NID মাস্ক করুন**।

## ৬ · ধাপ ৪ — নেগেটিভ টেস্ট চেকলিস্ট

> ⚠️ মূল রানবুকে **N1…N14** নামে ১৪টি টেস্ট ছিল; তার হুবহু সংজ্ঞা এই নথিতে নেই (❓)।
> নিচের তালিকা **D-02 অডিটের ১১টি চেক থেকে প্রত্যক্ষভাবে উদ্ভূত** — এগুলো অবশ্যই থাকতে হবে;
> মূল ফাইল পাওয়া গেলে N-সংখ্যা দিয়ে ম্যাপ করে নিতে হবে।

| # | টেস্ট | পদ্ধতি | পাস মানদণ্ড |
|---|---|---|---|
| ১ | Org A-এর user → Org B-এর ডেটা পড়া | সরাসরি কুয়েরি/API | ০ সারি বা 403 |
| ২ | Org A-এর user → Org B-তে লেখা | insert/update চেষ্টা | RLS প্রত্যাখ্যান |
| ৩ | ক্লায়েন্টের পাঠানো `organization_id` বদলে দেওয়া | manipulated request | সার্ভার উপেক্ষা করে; নিজের টেন্যান্টেই সীমাবদ্ধ |
| ৪ | `USING(true)` নীতি থাকা টেবিল | অডিট-১ ফল | কোনোটি না থাকা |
| ৫ | RLS বন্ধ টেবিল | অডিট-২ ফল | tenant টেবিলে আর নেই |
| ৬ | anon role → সরাসরি টেবিল | anon key দিয়ে পড়া | প্রত্যাখ্যাত |
| ৭ | Storage: Org A-এর ফাইল Org B থেকে | signed URL/সরাসরি | প্রত্যাখ্যাত |
| ৮ | Realtime: cross-tenant broadcast | সাবস্ক্রাইব | নিজের টেন্যান্টের ইভেন্ট ছাড়া কিছু আসে না |
| ৯ | গ্লোবাল `profiles.role='admin'` ব্যবহারকারী | tenant-বহির্ভূত অপারেশন | প্রত্যাখ্যাত |
| ১০ | `search_path` সেট না থাকা `SECURITY DEFINER` | অডিট-৩ ফল | সব ফাংশনে সেট |
| ১১ | Org A-এর admin → Org B-এর admin কাজ | UI + API দুটোই | সার্ভারে প্রত্যাখ্যান (UI লুকানো যথেষ্ট নয়) |
| ১২ | ডিলিট/রিভার্সাল | রসিদ বা লেনদেন delete চেষ্টা | ব্লকড; সংশোধন = বিপরীত এন্ট্রি |

## ৭ · ধাপ ৫ — Remediation প্রয়োগ (⛔ অনুমোদন-সাপেক্ষ)

`app/db/D01_zero_interest__MIGRATION_DRAFT.sql` ও `app/db/D02_tenant_isolation__REMEDIATION_DRAFT.sql`:
- প্রকৃতি: **additive / non-destructive** (DROP নেই, সারি UPDATE নেই)
- **একবারে একটি ধাপ**; প্রতিটি ধাপের পরে সংশ্লিষ্ট যাচাই-কুয়েরি (D02-এ ধাপ ৮) চালান
- D02 ধাপ ৬ (backfill) **ডিফল্টে বন্ধ** (`allow_single_org_backfill = false`) — চালু করা আপনার আলাদা অনুমোদন
- কোনো ধাপ ব্যর্থ হলে: `ON_ERROR_STOP` থাকায় সেটি থেমে যাবে; **আগের ধাপের ফল রিপোর্টে লিখে থামুন**

**পূর্বশর্ত (D02):** `is_org_member`, `is_org_admin`, `is_org_collector_or_admin`, `is_platform_admin`
হেল্পার ফাংশন আগে থেকে থাকতে হবে (না থাকলে `MULTI_TENANT_FOUNDATION_UP.sql`, ধাপ ২)।

## ১০ · ❓ যা এই নথিতে অজানা / যাচাই করা যায়নি
